# Приёмка новой установки

Это **не заполненный протокол успешных испытаний**. Сценарии ниже должны
быть выполнены на отдельной установке с её AD, SQL, сканером, репликой и
ролями. Демонстрационные скриншоты не закрывают ни один серверный тест.

## Предусловия

Собственные синтетические данные тестовой среды; не данные компании.
Минимум два независимых согласующих и два сеанса. Известен исходный пакет,
действующая версия бюджета, состояние резерва и точный источник платежа.
Внешние реальные отправки выключены. Есть резервная копия и план восстановления.

Для сценариев, которым нужен факт, сначала реализовать и принять
[штатный обмен](INTEGRATION_GUIDE.md). До этого соответствующие испытания
отмечать BLOCKED, а не PASS по скриншотам или вручную созданным SQL-записям.

При приёмке нового транспорта отдельно проверить: получение данных через
платформу 1С; минимальные права; неизменность результата при повторе;
обрыв постраничной выгрузки; неизвестную статью; частичную / полную оплату
и сторно; совпадение контрольных сумм источника и витрины BMS.

## Регистрация результата

Для каждого ID заполнить: дата/время; версия/хеш пакета; среда; роль и
область без пароля; входные условия; действия; ожидаемо; фактически;
точные суммы до/после; API/status/correlation; аудит/источник; PASS/FAIL/BLOCKED;
ответственный и ссылка на защищённое доказательство. Скриншоты реальных
данных не включать в публичный репозиторий.

## G. Отчёты и интерфейс

Проверить фильтры, сортировку, пагинацию, переход в карточку, сброс фильтров,
итоги всех строк, экспорт не только текущей страницы, неизвестные суммы,
пустые периоды, округление, дерево статей, разные роли. БДДС — факт/план
и процент; акрулы — первоначально/закрыто/остаток; должники — текущий PAID,
не неподдержанный прошлый срез; ОПиУ — только заявленное основание акрулов.

## Разрешение на рабочий запуск

Не включать неполную цепочку. При FAIL обязательного контроля сохранение
режима обслуживания и выключенных workers обязательно до решения владельца
процесса. Итог подписывает ответственный новой установки; владелец требований
по принятому бизнес-контексту — финансовый директор. Сроки / фамилии новой
организации заполняются при внедрении, не выдумываются из примеров.
