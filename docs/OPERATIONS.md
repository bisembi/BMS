# Эксплуатация, резервирование и восстановление

## Граница ответственности

Этот регламент предназначен для **новой собственной установки**.
Он не разрешает подключение к инфраструктуре первоначальной компании.
Не применять установщик новой БД как мигратор существующей рабочей базы.
Успешный старт службы не подтверждает свежесть данных и прохождение бизнес-цикла.

## До первого запуска

- Зафиксировать исходный архив, SHA-256 и `source-manifest.json`.
- Выполнить [проверку целостности](../setup/Test-BmsSourcePackage.ps1) до сборки.
- Проверить системные предпосылки [установки](INSTALLATION.md).
- Назначить отдельные Windows-учётные записи установщика, API и обмена.
- Подготовить SQL TLS, HTTPS, закрытое файловое хранилище и защищённый keyring.
- Разрешить службе только нужные SQL-права; не запускать её от DBA / sysadmin.
- Сохранить режим обслуживания; workers и SMTP остаются выключены.

## Включение рабочего режима

1. Получить подтверждённую конфигурацию новой установки без секретов в Git.
2. Сделать защищённую исходную резервную копию и проверить путь отката.
3. Настроить сотрудников / роли, справочники, матрицу и источники.
4. Пройти [приёмку](ACCEPTANCE.md) под разными реальными ролями.
5. Убедиться в восстановлении SQL, файлов, ключей и приватных настроек.
6. Согласовать включение фоновых операций, SMTP — отдельно.
7. Снять `BmsWeb__MaintenanceReadOnly` только после утверждения результатов.
8. Проверить UI, API, журналы, источники и первый контролируемый цикл.

Нельзя просто переключить все флаги `true`: настройки связаны друг с другом,
а некоторые workers требуют собственной служебной идентичности и профиля.

## Ежедневный чек-лист оператора

| Проверка | Признак нормы | Если не норма |
| --- | --- | --- |
| Служба и HTTPS | Процесс работает; адрес и сертификат соответствуют установке | Проверить логи и binding, не отключать вход / TLS |
| Вход и права | Реальный пользователь получает только назначенный доступ | Проверить SID, сотрудника, активность, роль и ЦФО |
| Свежее поколение факта | Период и завершение всех стадий подтверждены | Не объявлять старый снимок свежим, остановить публикацию неполноты |
| Оплаты | Очередной цикл сверки успешен; нет неоднозначных платежей | Не подтверждать догадками, исследовать источник |
| SQL | Диск и журнал имеют запас, нет блокирующей ошибки | Не удалять рабочие файлы БД; привлечь DBA |
| Вложения | Сканер и приватное хранилище доступны | Не переходить в разрешающий режим без сканера |
| Почта | Известны очередь, отправки, ошибки, неопределённые исходы | Не дублировать всю рассылку вслепую |
| Резервные копии | Есть актуальная копия и подтверждённое чтение метаданных | Не считать наличие файла доказанным восстановлением |

## Что резервировать

1. Основную SQL-БД с согласованной стратегией full / differential / log,
   выбранной DBA по модели восстановления и требованиям бизнеса.
2. Приватные вложения с соответствующей точкой согласованности SQL.
3. Ключи защиты данных / DPAPI и сведения о служебных идентичностях,
   необходимые для восстановления доступа.
4. Приватную конфигурацию службы и адаптеров, SMTP и расписания.
5. Опубликованный пакет бинарников и manifest, исходную версию и конфигурацию
   прокси / HTTPS без включения секретов в открытый архив.
6. Проверяемую информацию о последнем подтверждённом поколении источника,
   попытках отправок и контрольных суммах.

Срок хранения, RPO, RTO, место резервирования и ответственные **не заданы
пользователем для публичного пакета**. Их нужно утвердить на новой установке.
Не придумывать «ежедневная копия достаточна» без бизнес-требований.

## Восстановление — только в изолированную среду

Подготовить пустое изолированное окружение → остановить внешние отправки
и публикацию → восстановить SQL и согласованные вложения / ключи →
перенастроить сервисные права → оставить maintenance → проверить вход,
чтение документов и соответствие файлов → проверить версии схемы и пакета →
выполнить контрольную бизнес-приёмку → отдельно разрешить workers и почту.

Не отправлять реальные письма из восстановленной копии. Не подключать
тестовый обмен к рабочей БД. Не подменять отсутствующие ключи отключением
защиты или переносом секрета в appsettings Git.

## Обновление и откат

Для новой версии сначала определить совместимость SQL и бинарников,
сделать свежую резервную копию, собрать артефакт в стороне, проверить
права и миграции на копии. Сохранить прошлый пакет для отката. Во время
обновления не допускать пользовательских записей в несовместимую схему.

Откат бинарников не всегда равен откату данных. Если новая версия уже
записала новые циклы, решения или аналитики, нельзя молча вернуть SQL
с потерей действий сотрудников. Применять только согласованный совместимый
откат или восстановление с явным описанием потерь и компенсирующих шагов.

## Инцидент: неизвестный результат команды

Сначала перечитать документ и историю под той же ролью. Если интерфейс
предлагает повтор прежней попытки, использовать его. Не менять ключ
идемпотентности и не создавать новый документ как «повтор». Для обращения
сохранить correlation ID, время, номер заявки и безопасный текст ошибки.

## Инцидент: источник недоступен

Сохранить последний подтверждённый снимок, остановить публикацию частичного
поколения, проверить VPN/DNS/SQL/права/контракт. Старые данные не считать
актуальными. После восстановления сначала полный сбор и сверка, затем
атомарная публикация и контроль отсутствия дублей.

## Журналы и чувствительные данные

Отделять технические логи от бизнес-аудита и финансовых выгрузок. Не
добавлять дамп SQL, SMTP JSON, DSN, персональные SID и скриншоты реальных
документов в публичный issue. Сохранение журналов и доступ к ним настроить
по политике организации; конкретный срок здесь не выдумывается.
